Claude Code를 "그냥 쓰는 것"과 "잘 쓰는 것"은 결과 차이가 큽니다. 이 페이지는 공식 문서의 베스트 프랙티스와 실전 팁을 모았습니다.

---

## 사고 깊이 조절하기

Claude의 사고 모드(Extended Thinking)는 기본으로 켜져 있습니다. 작업 난이도에 따라 사고 깊이를 조절하면 속도와 비용을 최적화할 수 있습니다.

### Effort Level

`/effort` 명령으로 사고 깊이를 조절합니다.

| 레벨 | 용도 |
|------|------|
| `low` | 단순 작업. 빠르지만 추론 약함 |
| `medium` | 비용 절약이 중요한 일반 작업 |
| `high` | 대부분의 코딩 작업에 적합 |
| `xhigh` | Opus 4.7 기본값. 복잡한 에이전트 작업에 최적 |
| `max` | 최대 추론. 현재 세션에만 적용 |

> `low`~`xhigh`는 세션 간 유지되지만, `max`는 현재 세션에서만 유효합니다.

### UltraThink

프롬프트에 **"ultrathink"**를 포함하면 해당 턴에서 더 깊이 사고합니다.

```
ultrathink. 이 인증 시스템의 보안 취약점을 분석해줘
```

effort level 설정을 바꾸지 않고, 한 번만 깊게 생각하게 하고 싶을 때 유용합니다.

> "think", "think hard" 같은 문구는 일반 프롬프트로 처리됩니다. 사고 토큰을 추가로 할당하지 않습니다. 반드시 **"ultrathink"**를 사용하세요.

### 사고 모드 끄기

단순한 질문에는 사고 모드를 끄면 응답이 빨라집니다.

| 방법 | 범위 |
|------|------|
| `Option + T` (macOS) / `Alt + T` | 현재 세션 |
| `/config` → Think Mode → false | 모든 세션 (영구) |
| `MAX_THINKING_TOKENS=0` | 환경변수로 완전 비활성화 |

## 검증 수단을 제공하라

Claude Code를 잘 쓰는 가장 효과적인 방법 하나를 꼽으면: **Claude가 스스로 확인할 수 있게 하는 것**입니다.

| 상황 | 나쁜 예 | 좋은 예 |
|------|---------|---------|
| 함수 작성 | "이메일 검증 함수 만들어" | "이메일 검증 함수 만들어. user@example.com은 true, invalid은 false, user@.com은 false. 테스트도 작성하고 실행해" |
| UI 수정 | "대시보드 예쁘게 해줘" | "[스크린샷 붙여넣기] 이 디자인대로 구현해. 결과 스크린샷 찍고 원본과 비교해서 차이점 수정해" |
| 버그 수정 | "빌드가 안 돼" | "이 에러로 빌드 실패: [에러 붙여넣기]. 원인 찾아서 고치고 빌드 성공하는지 확인해" |

## 프롬프트를 구체적으로 작성하라

Claude는 의도를 추론할 수 있지만, 마음을 읽지는 못합니다.

| 전략 | 나쁜 예 | 좋은 예 |
|------|---------|---------|
| 범위 지정 | "foo.py에 테스트 추가해" | "foo.py에서 사용자 로그아웃 시 엣지 케이스 테스트를 작성해. mock 쓰지 마" |
| 패턴 참조 | "캘린더 위젯 만들어" | "홈페이지의 HotDogWidget.php 패턴을 따라서 캘린더 위젯 만들어" |
| 출처 지목 | "ExecutionFactory API가 왜 이상하지?" | "ExecutionFactory의 git 히스토리를 보고 API가 왜 이렇게 됐는지 요약해" |

### 풍부한 컨텍스트 제공하기

| 방법 | 사용법 |
|------|--------|
| `@파일명` | `@src/auth.js 설명해줘` — 파일 내용을 바로 포함 |
| 이미지 붙여넣기 | `Ctrl + V`로 스크린샷, 디자인 시안 등을 전달 |
| 파이프 입력 | `cat error.log \| claude` — 로그 파일을 바로 전달 |
| URL 참조 | 문서나 API 레퍼런스 URL을 직접 전달 |

## 탐색 → 계획 → 실행 → 커밋

큰 작업일수록 단계를 나눠서 진행하면 실수가 줄어듭니다.

**1단계: 탐색** (plan 모드)

```
/src/auth를 읽고 세션과 로그인이 어떻게 처리되는지 파악해
```

**2단계: 계획** (plan 모드)

```
Google OAuth를 추가하려면 어떤 파일을 수정해야 할까? 계획을 세워줘
```

> `Ctrl + G`로 플랜 파일을 에디터에서 직접 수정할 수 있습니다.

**3단계: 실행** (normal 모드로 전환)

```
계획대로 OAuth 플로우를 구현해. 콜백 핸들러 테스트 작성하고 실행해
```

**4단계: 커밋**

```
변경 내용을 커밋하고 PR 만들어줘
```

> 범위가 명확한 작은 작업(오타 수정, 변수 이름 변경 등)은 계획 없이 바로 실행해도 됩니다.

## 모델을 상황에 맞게 선택하라

| 모델 | 추천 상황 | 비용 |
|------|-----------|------|
| Sonnet | 대부분의 코딩 작업 | 낮음 |
| Opus | 복잡한 아키텍처 설계, 다단계 추론 | 높음 |
| Haiku | 서브에이전트의 단순 작업 | 매우 낮음 |

### opusplan — 계획은 Opus, 실행은 Sonnet

`opusplan` 모델 별칭을 사용하면 plan 모드에서는 Opus를, 실행 모드에서는 자동으로 Sonnet으로 전환합니다.

```bash
claude --model opusplan
```

계획 수립에는 Opus의 추론 능력을, 구현에는 Sonnet의 효율성을 활용하는 조합입니다.

## 컨텍스트를 적극 관리하라

Claude의 컨텍스트 윈도우는 대화, 파일, 명령어 출력으로 금방 찹니다. **컨텍스트가 차면 성능이 떨어집니다.** 이것이 가장 중요한 자원입니다.

### 핵심 규칙

| 상황 | 행동 |
|------|------|
| 다른 주제로 넘어갈 때 | `/clear`로 컨텍스트 초기화 |
| 2번 이상 수정 지시했는데 안 고쳐질 때 | `/clear` 후 더 구체적인 프롬프트로 새 세션 |
| 많은 파일을 조사해야 할 때 | 서브에이전트에 위임 (메인 컨텍스트 보호) |
| 대화가 길어졌을 때 | `/compact 코드 변경사항에 집중해`로 요약 |
| 컨텍스트에 안 남겨도 되는 질문 | `/btw`로 사이드 질문 (히스토리에 안 남음) |

### 서브에이전트 활용

조사를 서브에이전트에 위임하면 메인 컨텍스트를 깨끗하게 유지할 수 있습니다.

```
서브에이전트를 사용해서 인증 시스템이 토큰 갱신을 어떻게 처리하는지,
기존 OAuth 유틸리티가 있는지 조사해줘
```

서브에이전트는 별도 컨텍스트에서 파일을 읽고, 요약만 돌려줍니다.

## CLAUDE.md를 효과적으로 작성하라

`CLAUDE.md`는 매 세션 시작 시 로드됩니다. 짧고 핵심적이어야 합니다.

### 넣어야 할 것

- Claude가 추측할 수 없는 Bash 명령어
- 기본과 다른 코드 스타일 규칙
- 테스트 러너 및 실행 방법
- 브랜치 네이밍, PR 컨벤션
- 프로젝트 특유의 아키텍처 결정
- 환경변수 같은 개발 환경 특이사항

### 넣지 말아야 할 것

- 코드를 읽으면 알 수 있는 내용
- Claude가 이미 아는 표준 컨벤션
- 긴 API 문서 (링크로 대체)
- 자주 바뀌는 정보
- "깨끗한 코드를 작성하라" 같은 당연한 말

> CLAUDE.md가 너무 길면 Claude가 규칙을 무시합니다. 각 줄마다 "이걸 빼면 Claude가 실수할까?"를 자문하세요.

### /init으로 시작하기

```bash
claude
> /init
```

프로젝트 구조를 분석해서 기본 CLAUDE.md를 생성합니다. 여기서 다듬어 나가면 됩니다.

## Claude에게 인터뷰를 시켜라

큰 기능을 만들 때, 요구사항을 한 번에 완벽하게 쓰기 어렵습니다. Claude에게 **역으로 질문하게** 시키세요.

```
[간단한 설명]을 만들고 싶어. AskUserQuestion 도구로 나를 인터뷰해줘.

기술 구현, UI/UX, 엣지 케이스, 트레이드오프에 대해 물어봐.
뻔한 질문 말고, 내가 놓쳤을 수 있는 어려운 부분을 파고들어.

충분히 논의가 되면 SPEC.md에 완전한 스펙을 작성해.
```

스펙이 완성되면 **새 세션**에서 구현합니다. 깨끗한 컨텍스트에서 스펙만 보고 작업하는 게 효율적입니다.

## 실수 패턴과 해결법

| 실수 | 증상 | 해결 |
|------|------|------|
| 부엌 싱크대 세션 | 한 세션에서 무관한 작업을 계속 이어감 | `/clear`로 주제 전환 |
| 무한 수정 | 2번 이상 고쳐달라고 했는데 계속 틀림 | `/clear` + 배운 점을 반영한 새 프롬프트 |
| 뚱뚱한 CLAUDE.md | 규칙이 너무 많아서 Claude가 무시 | 200줄 이하로 유지. 나머지는 skill로 분리 |
| 무한 탐색 | "조사해줘"라고 했더니 수백 개 파일을 읽음 | 범위를 좁히거나 서브에이전트에 위임 |
| 검증 없는 신뢰 | 그럴듯해 보이지만 엣지 케이스를 놓침 | 항상 테스트/스크린샷/기대 출력을 제공 |

## 비용 절약 팁

| 방법 | 효과 |
|------|------|
| `/clear`로 자주 컨텍스트 초기화 | 매 메시지마다 처리하는 토큰 감소 |
| Sonnet을 기본으로, Opus는 필요할 때만 | 모델 비용 차이가 큼 |
| `/effort low`로 간단한 작업 처리 | 사고 토큰 절약 |
| 서브에이전트에 조사 위임 | 메인 컨텍스트에 파일 내용 안 쌓임 |
| CLAUDE.md를 짧게 유지 | 매 세션 로드 토큰 감소 |
| 자세한 워크플로우는 skill로 분리 | 호출 시에만 로드, 기본 컨텍스트 절약 |
| 사용 안 하는 MCP 서버 비활성화 | `/mcp`에서 확인 후 끄기 |

> `/cost`로 현재 세션의 토큰 사용량을 확인할 수 있습니다.
