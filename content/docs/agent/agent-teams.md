에이전트 팀(Agent Team)은 여러 개의 Claude Code 세션이 **팀을 이뤄 동시에** 작업하게 만드는 기능입니다. 한 세션이 팀장(lead), 나머지가 팀원(teammate) 역할을 맡고, 팀원끼리 직접 메시지를 주고받으면서 일을 나눠 처리합니다.

이 문서에서는 **에이전트 팀의 개념**, **서브에이전트와의 차이**, **활성화 방법**, **팀 시작과 제어**, **실전 사용 예시**, **알려진 한계**까지 다룹니다.

> **실험적 기능입니다.** 기본 비활성화 상태이며, 환경변수로 켜야 사용할 수 있습니다. Claude Code v2.1.32 이상 필요. (`claude --version`으로 확인)

---

## 비유: 부하 직원 한 명 vs 워크숍

| | 서브에이전트 | 에이전트 팀 |
|--|------------|-----------|
| 비유 | 팀장이 부하 직원 한 명에게 일 시키기 | 팀장이 워크숍 열기 |
| 협업 | 팀장 ↔ 직원 (1:1) | 팀원끼리 직접 토론, 도전 가능 |
| 결과 | 직원이 작업 후 보고서만 제출 | 모두 함께 결론 도출 |
| 비용 | 저렴 (요약만 메인으로 옴) | 비쌈 (각자 별도 Claude 인스턴스) |

서브에이전트는 **결과만** 메인에 돌려보냅니다. 에이전트 팀은 **팀원끼리 직접 메시지**를 주고받으며 협업합니다. 사용자도 팀원 누구에게나 직접 말을 걸 수 있습니다.

---

## 서브에이전트와 비교

| 항목 | 서브에이전트 | 에이전트 팀 |
|------|------------|-----------|
| **컨텍스트** | 자체 컨텍스트, 결과만 호출자에 반환 | 자체 컨텍스트, 완전 독립 |
| **소통** | 메인 에이전트에게만 보고 | 팀원끼리 직접 메시지 |
| **조율** | 메인 에이전트가 모두 관리 | 공유 작업 목록으로 자율 조율 |
| **적합한 작업** | 결과만 중요한 집중 작업 | 토론/협업이 필요한 복잡한 작업 |
| **토큰 비용** | 낮음 | 높음 (팀원 수만큼 비례) |

> **전환 시점** — 서브에이전트를 병렬로 띄우는데 컨텍스트 한계에 부딪히거나 워커끼리 통신이 필요해진다면 에이전트 팀으로 넘어갈 때입니다.

## 언제 에이전트 팀이 좋은가?

| 작업 | 이유 |
|------|------|
| 병렬 리서치/리뷰 | 보안/성능/테스트를 동시에 다른 시각으로 검토 |
| 새 모듈/기능 개발 | 팀원이 각자 다른 부분을 담당 (충돌 없음) |
| 경쟁 가설 디버깅 | 여러 가설을 동시에 검증하고 토론으로 수렴 |
| 크로스 레이어 작업 | 프론트엔드/백엔드/테스트를 각자 담당 |

### 쓰지 말아야 할 때

- **순차 작업** — 다음 단계가 이전 단계에 의존하는 경우
- **같은 파일 수정** — 팀원끼리 덮어쓰기 충돌 발생
- **단순 작업** — 토큰 비용만 늘어남
- **의존성 많은 작업** — 조율 오버헤드가 이득보다 큼

## 활성화

기본 비활성화입니다. `settings.json`에 환경변수를 추가하세요.

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

또는 셸에서 직접:

```bash
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
```

## 팀 시작하기

팀원을 정의하는 방식은 두 가지입니다.

| 방식 | 어떻게 | 언제 적합한가 |
|------|-------|-----------|
| **서브에이전트 기반** (권장) | 미리 정의한 [서브에이전트](../sub-agents)를 팀원으로 호출 | 반복 사용, 일관된 역할, 긴 작업 |
| **자연어 즉석 정의** | 그때그때 자연어로 역할 설명 | 일회성 탐색 |

> **왜 서브에이전트 기반이 권장인가?** 에이전트 팀은 `/resume`으로 복원되지 않습니다. 세션이 끊기면 팀원이 모두 사라지므로 다시 띄워야 합니다. 서브에이전트는 `.claude/agents/<이름>.md` 파일이 원본이라 같은 역할을 항상 동일하게 재현할 수 있고, git에 커밋하면 팀 전체가 공유할 수도 있습니다. 즉석 정의는 자연어 지시를 매번 다시 해석하는 방식이라 같은 팀이라도 결과가 달라질 수 있습니다.

### 방식 1: 서브에이전트 기반 (권장)

먼저 [서브에이전트](../sub-agents)를 정의해두고:

```
.claude/agents/
├── security-reviewer.md
├── perf-reviewer.md
└── test-reviewer.md
```

이름을 호출해서 팀원으로 띄웁니다.

```
PR #142 리뷰 팀 만들어줘.
서브에이전트 security-reviewer, perf-reviewer, test-reviewer를 팀원으로 사용.
```

서브에이전트의 `tools`, `model`이 그대로 적용되고, 본문은 팀원의 시스템 프롬프트에 추가됩니다.

> **주의:** 서브에이전트의 `skills`, `mcpServers` 필드는 팀원으로 동작할 때 적용되지 않습니다. Skill과 MCP 서버는 일반 세션처럼 프로젝트/사용자 설정에서 로드됩니다.

### 방식 2: 자연어 즉석 정의

서브에이전트로 박제하기 어색한 일회성 탐색이라면 자연어로 즉석 구성도 가능합니다.

```
TODO 주석 추적 CLI 도구를 설계 중입니다. 에이전트 팀을 만들어서
서로 다른 관점으로 살펴봐줘:
- UX 담당 한 명
- 기술 아키텍처 담당 한 명
- 반대 의견(devil's advocate) 담당 한 명
```

Claude가 역할별 시스템 프롬프트를 즉석에서 생성합니다. 빠르지만 세션이 끊기면 같은 팀을 동일하게 복원할 수 없습니다.

### 팀원 수와 모델 지정

```
4명의 팀원으로 이 모듈들을 병렬 리팩토링하는 팀을 만들어줘.
각 팀원은 Sonnet 모델 사용.
```

### Plan 승인 강제

위험한 작업은 팀원이 먼저 계획을 세우게 한 뒤 팀장이 승인해야 실행하도록 만들 수 있습니다.

```
인증 모듈 리팩토링을 위한 architect 팀원을 띄워줘.
변경 전에 plan 승인을 받도록 해줘.
```

팀원은 read-only plan 모드로 일하다가 계획을 팀장에게 제출. 팀장이 승인/거절합니다.

## 표시 모드

두 가지 모드가 있습니다.

| 모드 | 동작 | 요구사항 |
|------|------|---------|
| **In-process** (기본) | 한 터미널 안에서 팀원 전환 | 어떤 터미널이든 가능 |
| **Split-pane** | 팀원마다 별도 분할 화면 | tmux 또는 iTerm2 필요 |

기본값은 `auto`로, tmux 안에 있으면 split-pane, 아니면 in-process를 사용합니다. `~/.claude/settings.json`에서 강제 지정 가능:

```json
{
  "teammateMode": "in-process"
}
```

또는 한 세션만 강제:

```bash
claude --teammate-mode in-process
```

> tmux는 macOS에서 가장 잘 동작합니다. iTerm2 사용 시 `tmux -CC`가 권장 진입점입니다.

## 팀원과 직접 대화하기

각 팀원은 완전히 독립된 Claude Code 세션입니다. 팀장을 거치지 않고 직접 메시지를 보낼 수 있습니다.

| 모드 | 조작 |
|------|------|
| **In-process** | `Shift+Down`으로 팀원 전환 → 메시지 입력 |
| **In-process** | `Enter`로 팀원 세션 보기 / `Esc`로 현재 턴 인터럽트 |
| **In-process** | `Ctrl+T`로 작업 목록 토글 |
| **Split-pane** | 해당 pane 클릭 → 직접 입력 |

마지막 팀원에서 `Shift+Down`을 한 번 더 누르면 팀장으로 돌아옵니다.

## 작업 할당과 클레임

공유 작업 목록(task list)으로 팀원 간 작업이 조율됩니다. 작업은 3가지 상태를 가집니다.

- **pending** — 대기 중
- **in progress** — 작업 중
- **completed** — 완료

작업끼리 **의존성**도 설정 가능합니다. A가 B를 막고 있으면 B는 A가 끝나기 전에 클레임 불가.

### 할당 방식

| 방식 | 설명 |
|------|------|
| **팀장 지정** | 팀장이 누구에게 어떤 작업을 줄지 명시 |
| **자율 클레임** | 팀원이 끝나면 다음 가능한 작업을 스스로 가져감 |

> 동시에 같은 작업을 클레임하지 못하도록 파일 락이 걸립니다.

## 팀 종료와 정리

### 팀원 한 명 종료

```
researcher 팀원을 종료시켜줘
```

팀장이 종료 요청을 보냅니다. 팀원이 거절할 수도 있습니다.

### 팀 전체 정리

```
팀을 정리해줘
```

공유 리소스가 제거됩니다. 단, 활성 팀원이 있으면 실패 — 모두 종료한 뒤 정리하세요.

> **항상 팀장으로 정리하세요.** 팀원이 정리를 시도하면 컨텍스트가 잘못 풀려 리소스가 일관성 없는 상태로 남을 수 있습니다.

## 아키텍처

| 구성요소 | 역할 |
|---------|------|
| **팀장 (lead)** | 팀 생성, 팀원 스폰, 작업 조율 |
| **팀원 (teammates)** | 할당받은 작업 처리, 다른 팀원과 통신 |
| **작업 목록** | 공유된 작업 단위, 클레임/완료로 진행 |
| **메일박스** | 에이전트 간 메시징 시스템 |

저장 위치:

```
~/.claude/teams/{팀이름}/config.json    # 팀 설정 (자동 관리)
~/.claude/tasks/{팀이름}/                # 작업 목록
```

> **`config.json`을 직접 편집하지 마세요.** Claude Code가 상태 변경 시 덮어씁니다.

### 팀원이 받는 컨텍스트

팀원은 **팀장의 대화 기록을 상속받지 않습니다.** 일반 세션처럼 다음만 로드됩니다.

- `CLAUDE.md`
- MCP 서버
- Skills
- 팀장이 스폰 시 전달한 프롬프트

따라서 **스폰 프롬프트에 작업에 필요한 정보를 충분히 포함**해야 합니다.

```
다음 프롬프트로 security-reviewer 팀원을 스폰해줘:
"src/auth/ 인증 모듈을 보안 취약점 관점에서 리뷰. 토큰 처리, 세션 관리,
입력 검증에 집중. 앱은 httpOnly 쿠키에 JWT 토큰 저장. 발견한 이슈에
심각도 등급 매겨서 보고."
```

## 실전 예시

### 병렬 코드 리뷰

리뷰어 한 명은 보통 한 가지 이슈에 집중하게 됩니다. 팀으로 나누면 보안/성능/테스트를 동시에 깊게 볼 수 있습니다.

```
PR #142 리뷰를 위한 에이전트 팀을 만들어줘. 리뷰어 3명 스폰:
- 보안 영향 검토 담당
- 성능 영향 검토 담당
- 테스트 커버리지 검토 담당

각자 리뷰하고 결과 보고하게 해줘.
```

같은 PR을 다른 렌즈로 봅니다. 팀장이 끝에 결과를 종합합니다.

### 경쟁 가설 디버깅

근본 원인이 불명확할 때, 한 에이전트는 그럴듯한 설명 하나를 찾고 멈추는 경향이 있습니다. 팀원들이 서로의 가설을 **반박하게** 만들면 진짜 원인이 살아남습니다.

```
사용자가 메시지 한 번 보내면 앱이 종료된다고 보고함.
팀원 5명을 띄워서 서로 다른 가설을 조사하게 해줘.
서로 대화하면서 상대 이론을 반박하는 과학 토론처럼 진행.
합의된 결론을 findings 문서에 업데이트.
```

순차 조사는 **앵커링 편향**(첫 가설에 끌려감)에 빠지기 쉽습니다. 독립된 조사자가 서로 도전하면 살아남는 가설이 실제 근본 원인일 확률이 높습니다.

## Hooks로 품질 게이트 강제

팀원이 작업을 끝내거나 작업이 생성/완료될 때 [hooks](https://code.claude.com/docs/en/hooks)로 규칙을 강제할 수 있습니다.

| 훅 이벤트 | 발동 시점 |
|----------|---------|
| `TeammateIdle` | 팀원이 idle 상태로 가려 할 때. exit 2로 피드백 보내고 계속 일 시킴 |
| `TaskCreated` | 작업 생성 시. exit 2로 생성 차단 |
| `TaskCompleted` | 작업 완료 표시 시. exit 2로 완료 차단하고 피드백 |

## 모범 사례

### 팀원에게 충분한 컨텍스트 주기

팀원은 팀장의 대화 기록을 못 봅니다. 스폰 프롬프트에 작업별 세부사항을 명시하세요.

### 적정 팀 크기

| 권장 | 이유 |
|------|------|
| **3~5명** | 대부분의 워크플로우에 적합 |
| **팀원당 작업 5~6개** | 컨텍스트 스위칭 부담 없이 생산성 유지 |

토큰 비용은 팀원 수에 **선형 증가**합니다. 더 많이 띄운다고 비례해서 빨라지지 않습니다. **흩어진 5명보다 집중된 3명**이 보통 더 낫습니다.

### 작업 크기

- **너무 작음** — 조율 오버헤드가 이득보다 큼
- **너무 큼** — 체크인 없이 오래 일해서 헛수고 위험
- **적절** — 함수 하나, 테스트 파일 하나, 리뷰 한 건 같은 자기완결적 단위

### 파일 충돌 피하기

두 팀원이 같은 파일을 편집하면 덮어쓰기가 발생합니다. **팀원마다 다른 파일을 담당**하도록 작업을 나누세요.

### 처음에는 리서치/리뷰부터

코드 작성보다 **PR 리뷰, 라이브러리 조사, 버그 조사** 같은 작업으로 시작하세요. 경계가 명확하고 병렬 탐색의 가치를 빠르게 느낄 수 있습니다.

### 팀장이 직접 일하면 막기

팀장이 팀원을 기다리지 않고 직접 일하기 시작하면:

```
팀원들이 작업을 끝낼 때까지 기다려줘
```

## 알려진 한계

실험적 기능이라 다음 제약이 있습니다.

| 한계 | 설명 |
|------|------|
| **세션 재개 불가** | `/resume`/`/rewind`로 in-process 팀원 복원 안 됨. 재개 후 새 팀원 스폰 필요 |
| **작업 상태 지연** | 팀원이 가끔 작업 완료 표시를 누락 → 의존 작업 블로킹 |
| **종료가 느림** | 팀원이 현재 요청/도구 호출을 끝내야 종료 |
| **세션당 팀 1개** | 새 팀 시작 전 기존 팀 정리 필요 |
| **중첩 팀 불가** | 팀원이 자기 팀을 만들 수 없음 |
| **팀장 고정** | 팀장 교체 불가, 팀장이었던 세션이 끝까지 팀장 |
| **권한 통일** | 팀원은 팀장의 권한 모드로 시작 (스폰 시 개별 모드 지정 불가) |
| **분할 화면 제약** | VS Code 통합 터미널, Windows Terminal, Ghostty에서 split-pane 미지원 |

## 토큰 비용 주의

에이전트 팀은 단일 세션보다 **훨씬 많은 토큰**을 사용합니다. 각 팀원이 자체 컨텍스트 윈도우를 가지고, 토큰 사용량이 팀원 수에 비례합니다.

| 사용 적합 | 비용 부담이 정당화됨 |
|----------|------------------|
| 리서치 | ✅ 가치 충분 |
| 리뷰 | ✅ 가치 충분 |
| 새 기능 개발 | ✅ 가치 충분 |
| 일상적 단순 작업 | ❌ 단일 세션이 더 효율적 |

## 활용 가이드

- **팀원은 [서브에이전트](../sub-agents)로 먼저 정의하세요.** 세션이 끊겨도 같은 팀을 그대로 부활시킬 수 있고, git 커밋으로 팀에 공유도 됩니다. 즉석 정의는 일회성 탐색에만 사용하세요.
- **처음에는 코드 리뷰부터.** PR 하나에 보안/성능/테스트 리뷰어 3명을 띄워보세요. 병렬 탐색의 효과를 체감하기 좋습니다.
- **디버깅이 막히면 경쟁 가설 팀.** 5명한테 서로 다른 이론을 반박하게 시키면 단일 세션보다 빨리 진짜 원인에 도달합니다.
- **새 모듈을 처음부터 만들 때.** 팀원에게 모듈/계층을 나눠주면 충돌 없이 병렬로 진행됩니다.
- **팀원 3~5명을 기본값으로.** 더 많이 띄우면 조율 비용만 늘어납니다.
- **단순 작업은 단일 세션 또는 서브에이전트로.** 에이전트 팀의 토큰 비용을 정당화할 만한 작업인지 먼저 판단하세요.
